Only decisions that can be verified from the repository, `docs/design.md`, the live project, or that were made during the creation of `.ai/` are listed.
"Owner" = the project owner (the person the agents work for). Dates are approximate where the exact day is not recorded (the requirements interview ran over several days in September 2026).
"Active" means the decision is still in force. Do not reverse an active decision without recording a new decision that explains why.

## DEC-001 — Build v2 in a separate Supabase project; keep v1 running
- Date: 2026-09 (D-11, interview); project created 2026-09-20 (migration timestamps).
- Context: v1 is live for real classes; v2 changes almost everything.
- Reason: zero risk to v1; free plan allows two projects (cost checked: $0).
- Alternatives: same project with v2 tables next to v1 (risk to live exams); paid branching (~$0.013/hour).
- Consequences: two projects, two configurations; v2 becomes production later; v1 result data is archived at cutover (DEC-016).
- Affected: whole repository; `supabase/README.md`. Active: yes.

## DEC-002 — All data access through Edge Functions; RLS on with zero policies; no grants to anon/authenticated
- Date: 2026-09-20 (`v2_05_lockdown`); pattern inherited from v1.
- Reason: keeps answer keys and student data away from browsers even if the publishable key leaks.
- Consequences: no Supabase client in the browser for data; every feature needs an Edge Function endpoint + SQL functions.
- Affected: all tables, all functions, `frontend/assets/js/core/api.js`. Active: yes. PROTECTED.

## DEC-003 — Staff authentication with Supabase Auth; role read from `profiles`; `verify_jwt=false` with in-code verification
- Date: 2026-09-20 (D-07 approved split Teacher/Admin).

## DEC-004 — Business rules as SQL functions (one transaction per action, audit inside); Edge Functions only validate, clean, and call
- Date: 2026-09-20.
- Reason: multi-step writes (question + answers + labels + files + audit) must be atomic; supabase-js has no cross-call transactions; rules become testable directly in SQL.
- Consequences: schema and rules live in the database; duplicated validation exists on purpose (friendly Edge messages + authoritative SQL checks).
- Affected: migrations `v2_08`, `v2_09`, `v2_12`; `backend/functions/*/handler.ts`, `parse.ts`. Active: yes. PROTECTED.

## DEC-005 — Shared text normalization and content-hash rules in JS and SQL
- Date: 2026-09-20 (`v2_07` fixed a trailing-space bug and made ordering locale independent).
- Decision: normalization = collapse whitespace, trim, lower-case. Content hash = SHA-256 of normalized body + "\n" + normalized options sorted by UTF-8 bytes (`collate "C"` in SQL). Names and classes are compared normalized (D-08, D-01).
- Reason: the browser/server must agree on "same student", "same class", "same question".
- Affected: `backend/functions/_shared/text.ts`, SQL `normalize_text`, `question_content_hash`, generated columns on `exam_sessions`, `question_class_labels`, `accepted_answers`. Verified: hashes from `text.ts` equal hashes stored in the database (test in `shared.test.ts`). Active: yes. PROTECTED: change both sides together.

## DEC-020 — Two-branch Git workflow: `main` (stable) and `ai-development` (shared sequential AI branch)
- Date: 2026-09-21 (owner's request, implemented by Claude).
- Decision: `main` is the stable branch and is not used as the normal AI workspace. `ai-development` is where Claude and Codex/GPT do normal, everyday development. `ai-development` was created from `main` at commit `46803f0` (the commit that added `.ai/`). Only one AI actively modifies `ai-development` at a time — Claude and Codex/GPT are not expected to work on it simultaneously, they take turns sequentially (Claude → Codex/GPT → Claude → ...), each pulling the latest state, reading `08_HANDOFF.md`, doing a unit of work, testing, updating `.ai/`, committing, and pushing before the next agent starts.
- Reason: with two different AI systems (Claude and Codex/GPT) potentially touching the same repository at different times, working directly on `main` risks leaving it in a broken or half-finished state between hand-offs. A dedicated development branch lets work-in-progress accumulate safely while `main` keeps representing "the last version someone deliberately decided was stable."
- Why sequential, not concurrent: neither agent has a way to lock files or negotiate a merge with the other in real time within this workflow; a single shared branch worked on one-at-a-time (rather than each agent branching further and merging) keeps history linear and avoids merge conflicts between two AI agents that cannot coordinate directly.
- Why merging into `main` is deliberate rather than automatic: the owner (or whoever reviews the project) should be the one who decides a batch of AI work is ready to become "the stable version," not an agent mid-task. An agent finishing one task on `ai-development` does not imply the whole branch is stable — earlier work on the same branch might still be incomplete (as it is right now: TASK-006 is mid-flight).
- Alternatives considered: (a) one agent per feature branch, merged via pull request — more standard, but assumes both agents and a reviewer can manage PRs, which was not confirmed as available; (b) working directly on `main` with frequent small commits — rejected per the owner's explicit instruction and the risk above.
- Consequences: every task description in `05_TASK_QUEUE.md` and every entry in `08_HANDOFF.md` must state which branch the work is on. `00_AI_RULES.md` section 12 has the operational rules. The existing single-branch history (`35d6561` through `46803f0`) stays on `main` unchanged; only new work moves to `ai-development`.
- Affected: repository branch structure only; no application code, database, or UI changed because of this decision.
- Active: yes.

## DEC-022 — A student's session is a signed token (no accounts, no token column)
- Date: 2026-09-23 (made by Buffy while building the student exam engine, TASK-010).
- Context: students have no accounts (DEC-003 covers staff only). Something must prove to `get`, `save`, `submit`, `event`, `media` and `result` that the caller is the browser that joined a given session. The design's data model for `exam_sessions` has no token column, and the server must never trust a name/class sent back by the browser.
- Decision: `join` returns `<session id>.<signature>`, where the signature is `base64url(HMAC-SHA256(key, "session:" + session id))` and the key is the function secret `SESSION_TOKEN_SECRET` (falling back to `SUPABASE_SERVICE_ROLE_KEY`, which every function already has and which never reaches a browser). The Edge Function verifies it on every other action and passes only the session id to SQL. Verification (`backend/functions/session/token.ts`) compares all characters and rejects a missing/foreign signature.
- Reason: the session id is a UUIDv4 and unguessable, but this way a leaked id (a teacher screen URL later, a log line) is not enough to read or write another student's answers; nothing secret is stored at rest, no column was added to a PROTECTED table, and the browser holds one opaque string.
- Alternatives: (a) the raw session id as the only credential — simplest, but any leak of an id would be a full write capability; (b) a random token column on `exam_sessions` — same strength, but needs a schema change (a migration on a table owned by Phase 1) and stores another secret in the database; (c) a Supabase Auth anonymous sign-in per student — heavy, needs sign-ups enabled, and ISSUE-007 wants them off.
- Consequences: the token must be kept by the browser (`localStorage`, key `ENGLISH_TEST_V2_STUDENT_SESSION`) to survive a reload, and rotating `SESSION_TOKEN_SECRET` logs every running student out. The token carries no expiry of its own: the session's own `ends_at`/status is the authority.
- Affected: `backend/functions/session/{handler.ts,token.ts}`, `frontend/assets/js/student/{api.js,store.js}`. Active: yes.

## DEC-023 — A result is written in exactly one place, and a hand-made grade outranks an automatic one
- Date: 2026-09-24 (made by Buffy while building the teacher grading side, TASK-012).
- Context: TASK-010 wrote `exam_results` inside `_session_grade`, which the submit path called. TASK-012 introduces a second writer path (a teacher grading one answer, correcting another, or a re-grade after a `reopen` + second submit). Two writers of a row whose `status` and `pass_status` must stay consistent (the table has a CHECK tying them together) would drift apart; and a re-grade would silently overwrite a teacher's correction with the automatically computed points.
- Decision: `_session_result_write(session_id)` is the **only** function that inserts/updates `exam_results` — it recomputes points, percentage, right/wrong, `status`, `pass_status` and the review from the stored `answer_grades` plus the session snapshot, and both the submit path and every manual grade call it. `_session_grade` was re-created (replacing TASK-010's version) so that a question whose `answer_grades.is_auto` is false is **skipped** on re-grade: an automatic pass never touches a hand-made grade. A blank essay still counts as an answered question worth 0 points, so the result stays honest rather than silently final.
- Reason: one writer keeps `status`/`pass_status` coherent no matter which path runs, and BR-18 (the teacher's correction is final) is enforced in the database rather than in the UI.
- Alternatives: (a) let each action recompute and write the row itself (simplest to read, but three copies of the same arithmetic and a real drift risk); (b) keep the old `_session_grade` and skip hand-graded questions only in the UI (a `reopen` + resubmit would silently revert a correction — rejected); (c) add a `manually_graded` flag to `exam_results` instead of reading `answer_grades.is_auto` (a schema change with no extra benefit: the fact already lives on the grade row).
- Consequences: `_session_grade` is the only TASK-010 object changed by TASK-012; any future path that changes a grade must call `_session_result_write` rather than write the table. The stored `review_snapshot` is the source the statistics screens will read, so it must keep carrying the per-question detail.
- Affected: `supabase/migrations/20260924000000_result_functions.sql`, `docs/sql-results.md`, `backend/functions/results/*`, `frontend/assets/js/teacher/screens/{grading,gradingQuestion,sessionReport}.js`. Active: yes.

## DEC-024 — A monitor reads, never writes; and more time for a whole exam is one audited action
- Date: 2026-09-24 (decided by the eleventh session's owner-guided reconciliation, after two agents had built the monitor in parallel).
- Context: a teacher leaves the board open on a laptop while a class works, so it refreshes on its own (hub 30 s, per-exam board 15 s). That makes two temptations real: writing something onto a session while drawing the board (a status like `offline`), and letting the browser decide what a row means. A class that started late also needs "everyone still working gets five more minutes" without the teacher clicking through every student.
- Decision: the monitor's read is `list_exam_results` — `stable`, writes nothing, includes in-progress attempts. "Offline" and the one status label per row ("Saved" / "Left the page" / "Need a look" / Offline) are judgements made at read time, from the exam's own `tab_switch_warn_limit` / `tab_switch_flag_limit` (which the payload must therefore carry) and `last_heartbeat_at`. The browser only maps what it was given; it never computes a state. The single write the board offers is `add_exam_time(p_exam_id, p_seconds, p_actor)`: the exam-scope twin of BR-11, one transaction for every running attempt, one audit row, one `time_added` event per session (`meta.scope = 'exam'`), and `last_heartbeat_at` refreshed so the teacher's own action cannot flip the class to "offline". There is exactly **one** read path: `list_live_sessions` was dropped rather than kept beside `list_exam_results`.
- Reason: a board a teacher watches must be incapable of changing what a student is doing — a refresh, or a second teacher idly looking at it, must not touch a session. Computing "offline" at read time avoids a status that goes stale the moment the phone reconnects, and needs no schema change. One exam-wide action keeps BR-11 auditable in one row instead of N. One read path matters because a second one is how a payload and its screen drift apart — which is exactly what ISSUE-021 turned out to be.
- Alternatives: (a) write an `offline`/`left_page` status onto `exam_sessions` — a schema change on a PROTECTED table plus a judgement that stays on the row after the phone comes back (rejected); (b) let the browser compute the ladder from raw counters — it would then exist twice and drift from the report (rejected); (c) loop `add_session_time` from the Edge Function — the action would stop being one transaction and its audit trail would become N unrelated rows (rejected); (d) keep both read functions "just in case" — that is the drift the tenth and eleventh sessions collided over (rejected).
- Consequences: a new monitor state or pill must reach the screen through this payload, and the payload must carry every number the pill reads. `add_exam_time` refuses a 0-minute step, more than 2 hours, and an exam with nobody working, so a mis-click cannot write an audit row that says nothing happened. The students' phones need no change: they read `ends_at` from the server on each heartbeat (BR-20).
- Affected: `supabase/migrations/20260925000000_monitor_overview_fields.sql`, `supabase/migrations/20260927000000_exam_wide_add_time.sql`, `docs/sql-monitor.md`, `backend/functions/results/{handler.ts,parse.ts}`, `frontend/assets/js/teacher/{screens/examMonitor.js,screens/sessionTimeline.js,components/resultBits.js,api/results.js}`, `frontend/tests/{monitor_e2e.py,live_monitor_check.py,live_browser_check.py}`. Active: yes.

## DEC-027 — An exam with attempts is closed by a teacher and only permanently deleted by an admin
- Date: 2026-09-25 (owner decision, ISSUE-023; made by Buffy).
- Context: `remove_exam` closed an exam that had attempts and answered `'closed'`, while the exams screen's Delete button had just asked "Delete this exam?" and promised the exam "will be removed". The owner hit Delete five times on the same exam on 2026-09-25 (five `exam.close` audit rows, `delete requested while sessions exist`) — the button and the dialog were lying about what would happen. The underlying rule is real (BR-10 / DEC-012: an attempt and its result are never lost), but the *interface* was the defect.
- Decision: **three explicit behaviours instead of one silent one.** (1) `list_exams` reports `session_count`, so the screen knows before the click. (2) A **teacher** gets no Delete button on an exam with attempts at all — the row says "N attempts — kept for the results" and the ordinary Open/Close toggle is the only way out; the SQL still closes the exam if the request arrives anyway (`p_force = false`). (3) A **permanent delete** exists but is **admin-only**: the `exams` Edge Function passes `p_force = true` only for the admin role (`requireStaff(req, db, ["admin"])`), the dialog names the attempt count and says the answers, grades and results go with it, and the audit row is `exam.delete` with `attempts` and `permanent: true`. The destructive work is one SQL transaction inside `remove_exam` (DEC-004).
- Reason: the owner's answer to "what should happen?" was "Close for teachers, permanent delete for the admin only" — that keeps the data-protection rule for everyday use while giving the one role that owns the system a way to really remove a mistake (a mistyped practice exam, a duplicate). Making it *visible* (attempt count + honest dialog) is what stops the click-loop; the role split is what keeps DEC-012 meaningful for teachers.
- Alternatives: (a) only reword the dialog (rejected: the button still cannot delete, so the loop would return under time pressure); (b) let a teacher permanently delete too (rejected by the owner: an accidental click would destroy a class's attempts); (c) delete attempts but keep the results as orphans (rejected: a result without its session is unreadable and `exam_results.session_id` is `NOT NULL`); (d) allow deletion only when no attempt has been *submitted* (rejected: abandoned attempts still hold a snapshot and answers, and the rule would be harder to explain in one line).
- Consequences: `remove_exam` now takes `p_force` and the old two-argument function was **dropped** (no force-less overload may survive, or one could delete by accident); the exams screen must pass the role it already receives in `ctx`, and any future caller must decide explicitly. The screen's row text and dialog are the contract the browser tests pin: `exams_e2e.py` switches the mock's role to check both sides. Live-verified end to end: `frontend/tests/live_exam_delete_check.py` (17/17).
- Affected: `supabase/migrations/20260930000000_exam_delete_with_attempts.sql`, `backend/functions/exams/handler.ts`, `frontend/assets/js/teacher/{api/exams.js,screens/exams.js}`, `backend/tests/exams.test.ts`, `frontend/tests/{exams_e2e.py,mock_server.py,live_exam_delete_check.py}`, `docs/sql-exams.md`. Active: yes.

## DEC-028 — Live-only SQL is committed verbatim from the migration history, not re-implemented
- Date: 2026-09-25 (made by Buffy on the owner's instruction, resolving ISSUE-024).
- Context: an earlier session applied TASK-020's `find_duplicate_groups` to the live project (tracked as `v2_17_duplicate_overview` + a `search_path` follow-up at 06:06 UTC) and deployed a `duplicate_groups` action on `question-bank`, but committed **nothing**: the live database was ahead of every branch. The same shape of problem as the Codex/GPT import collision (ISSUE-015, DEC-021), where the wrong answer — writing a second implementation — cost this project a manual reconciliation.

Match the Edge layer to the deployed function (verified by re-downloading it and comparing) instead of guessing, and write the missing pieces on top of the recovered contract. Never re-apply the statements to the live database and never write a competing implementation of the same SQL.
- Reason: the migration history already stores the statements — so this is a copy, not a design decision, and it makes the live row and the file agree. Using the live version numbers as file names means a later `supabase db push` recognises them as applied (the round-numbered names the older files use are what caused ISSUE-001's "these look unapplied" trap). Re-typing the SQL by hand would reintroduce exactly the drift being fixed; `create or replace` makes a stray re-apply harmless but pointless.
- Alternatives: (a) re-implement the scan from the mockup (rejected — two implementations of one scan is the DEC-021 mistake again, and the live ACL/behaviour is already proven); (b) leave it live-only and document it (rejected by the owner: the database must be rebuildable from git); (c) rename the files to the folder's round-numbered convention (rejected — it would hide that the live row is already applied); (d) recover the function body with `pg_get_functiondef` (rejected as the primary source: it reformats the text, so it would not be verbatim).
- Consequences: `docs/sql-duplicates.md` carries a small script that re-proves verbatim-ness against the live rows, and every future "live-only SQL" find should follow this route. Two more files now sit in `supabase/migrations/` whose names are not round numbers — that is deliberate and is the honest record of what the live project went through. **A live-only migration is no longer a blocker, only a missing copy.**
- Affected: `supabase/migrations/20260925060607_v2_17_duplicate_overview.sql`, `supabase/migrations/20260925060638_v2_17_duplicate_overview_fix_search_path.sql`, `backend/functions/question-bank/handler.ts`, `docs/sql-duplicates.md`, `.ai/09_KNOWN_ISSUES.md` (ISSUE-024 closed). Active: yes.

## DEC-025 — The exports are built in the browser, and both files come from one table
- Date: 2026-09-24 (made by Buffy while building the Excel export, TASK-012).
- Context: mockup 14 puts Excel, CSV and "PDF class summary" on the results screen, and the design document lists CSV/Excel/PDF under Phase 4. A teacher would rather open a spreadsheet than a web page, and the screen already holds every number. Two questions had to be answered: where the file is made (browser or Edge Function) and how two formats stay identical.
- Decision: the **browser** writes both files, with **no new dependency** — `frontend/assets/js/teacher/export/zip.js` (a ZIP writer whose entries are stored, CRC-32 computed in JavaScript) plus `xlsx.js` (`buildXlsx`) and one shared `resultsTable.js` that both exports are built from. Text cells become inline strings with every XML metacharacter escaped and control characters dropped; numbers stay numbers so Excel can sort and average them. ## DEC-029 — Housekeeping runs in the database on a schedule; the one job that needs Storage goes through the function with a narrow key
- Date: 2026-09-26 (made by Buffy while finishing TASK-015's scheduled purge jobs; the key approach was the owner's choice).
- Context: `expire_sessions`, `purge_rate_limits` and `purge_orphan_media` had existed since the student engine, the rate limiter and the media flow were built, but **nothing called them** (ISSUE-012, ISSUE-018): a student who closed the browser stayed `in_progress` forever, spent rate-limit windows accumulated, and uploads nobody attached stayed in the bucket. Two of the three are pure SQL. The third is not: `purge_orphan_media()` deletes the `media_files` rows but the **bytes live in Storage and can only be removed through the Storage API** — the `media` function's `purge_unused` action does exactly that for an admin, and a database-only job would delete the rows and leak the files silently. The owner was asked how the nightly sweep should be let in and chose *a narrow housekeeping key, not the service-role key*.
- Decision: (1) **the clock lives inside the database** — `pg_cron` (enabled by this migration) runs `expire-sessions` every five minutes and `purge-rate-limits` nightly, calling the SQL functions directly; (2) the **media job is a `pg_net` HTTP call to the deployed `media` function** with `{"action": "purge_unused"}`, so the bytes really go away; (3) that call authenticates with a **housekeeping key** — generated in the migration into Supabase Vault, mirrored as the function secret `HOUSEKEEPING_KEY`, SHA-256-compared in `_shared/auth.ts#isScheduledJob`, and opening **exactly one action** (the handler returns before `requireStaff`, so the key never becomes a staff identity); (4) the migration is applied through the Management API **and inserts its own `supabase_migrations.schema_migrations` row**, because applying that way leaves no tracking row and a silent "not applied remotely" is exactly ISSUE-001's drift.
- Reason: the jobs must run whether or not anybody is signed in, and the database is the only always-on part of this project (there is no hosting yet — TASK-017). Keeping the two pure-SQL jobs as plain SQL keeps them testable in SQL and immune to HTTP failures; sending only the Storage-dependent one through the function keeps the one thing that must not happen — deleting bookkeeping rows while leaving the files — impossible by construction. The key is deliberately narrower than the service-role key: it is one action's worth of authority, it never appears in the repository (a live check greps the whole tree for it), and the roles that could reach `cron`/`vault` at all have no schema access.
- Alternatives: (a) a pure-SQL media job (rejected — deletes the rows and silently leaks the bytes, which is worse than doing nothing); (b) the service-role key in Vault (rejected by the owner — the database would hold the project's master key for a housekeeping chore); (c) leave the purge to the admin's button (rejected — orphan files are precisely what nobody remembers, and TASK-015 asks for a schedule); (d) an external scheduler calling the functions (rejected — nothing outside the project exists to run it yet, and it would be another credential to manage).
- Consequences: three `cron.job` rows are now part of the live contract (`supabase/tests/scheduled_jobs_test.sql` asserts their schedules, commands and role); the media function has a second, machine-only door that must stay closed to everything but `purge_unused` (`media.test.ts` pins that, and the live check proves a wrong key, another action and a tokenless call are all 401); the key now exists in **three places** that must agree — Vault, the function secret, and nothing else — so rotating it is a two-step operation documented in `docs/sql-jobs.md`. Any future scheduled work (a nightly backup, for instance) can reuse the same pattern.

## DEC-030 — A backup is one file holding the whole database plus the media bytes; the newest seven nightly copies are kept and manual copies until an admin deletes them
- Date: 2026-09-26 (made by Buffy while building TASK-015's backup slice; all three content/retention/screen choices were the owner's).

## DEC-034 — `ALLOWED_ORIGIN` is an allow-list; the caller's own origin is echoed back only when it is on it
- Date: 2026-09-28 (production-readiness session, before hosting exists).
- Context: `_shared/http.ts` answered every browser with `Access-Control-Allow-Origin: <the ALLOWED_ORIGIN secret>`, defaulting to `*`, and the secret could hold exactly one value. That is enough to lock the API to one address once the app is hosted, but it leaves the owner choosing between the live address and a local test address, and it does not say out loud that an off-list website must not be served. Hosting is the last thing between this project and real students (TASK-017).
- Decision: the secret now accepts **one origin, or several separated by commas** (so `https://<app>,http://localhost:8000` works), and `corsHeaders(req)` **echoes the caller's own `Origin` only when it is on that list**. Unset, empty, or a `*` entry keeps the old wildcard behaviour (development). A caller with no `Origin` header at all — curl, the scheduled housekeeping job — gets the first entry, which nothing enforces for a non-browser. Whenever the answer is not `*` it also carries **`Vary: Origin`**, so a per-caller header can never be cached and handed to a different caller. The comparison is a plain list membership test: **no credentials are involved**, because staff tokens travel in the `Authorization` header and never in cookies, which is also why no `Access-Control-Allow-Credentials` is needed and the wildcard stays usable.
- Reason: this is the smallest change that makes the production setting expressible, and it fails safe — an off-list website is answered with a name that is not its own, so its browser refuses to hand the response over (the same outcome as today's fixed value). The origin is resolved per request, so changing the secret needs no redeploy.
- Alternatives: (a) keep one value and tell the owner to set only the live address (rejected — the local address is genuinely useful for testing against the live backend, and a second value costs nothing); (b) a `*` regex/path matcher over the origin (rejected — more ways to write a wrong rule, and no requirement asks for subdomain matching); (c) echo whatever `Origin` arrives and let the browser sort it out (rejected — that is precisely "allow any website" with extra steps); (d) cookies instead of bearer tokens (rejected — a much larger change to DEC-003's design, with a CSRF surface this API does not need today).
- Consequences: `frontend/_headers`, `docs/production-deployment.md` step 2 and `backend/README.md` document the list form; the four new tests in `backend/tests/shared.test.ts` pin the wildcard default, the echo, the refusal to echo a stranger, the comma-separated list, and that **every** response `handle` builds (success, an `ApiError`, and the `OPTIONS` preflight) carries the answer. Existing deployments are unaffected: with one value and one caller the header is byte-identical to before.
- Affected: `backend/functions/_shared/http.ts`, `backend/tests/shared.test.ts`, `backend/README.md`, `.ai/02_ARCHITECTURE.md`, `docs/production-deployment.md`, `docs/verification-checklist.md`. Active: yes.

## DEC-035 — Changing many questions is one database act (`bulk_update_questions`), "keep as it is" is an absent key, and a selection over 500 is refused rather than trimmed
- Date: 2026-09-28 (bulk question management session; the SQL was written that day and **applied + live-verified the same day**, once the owner supplied a Supabase credential — see ISSUE-033, now closed).
- Context: the question bank let a teacher change one question at a time. F-05/F-17 asks for the other half: tick many, say what should change, check what will happen, then have it happen. The obvious shortcut is a loop of `save` calls from the browser — which can stop half way, writes one audit row per question, and sends the whole question text forty times over the wire.
- Decision: (1) **one database function, one transaction, one audit entry** — `public.bulk_update_questions(p_ids uuid[], p_changes jsonb, p_actor uuid)` follows DEC-004 exactly as `save_question` does, so forty questions change or none do and the trail records one act (`question.bulk_update`, with the real count and what was asked for); (2) **"keep as it is" is an absent key, never a sentinel value** — the Edge layer's `parseBulkUpdate` whitelists `topic` / `difficulty` / `weight` / `archived` / `class_labels`, so a caller cannot smuggle `body`, `options` or `content_hash` through a bulk change, and the database never has to interpret the word "keep"; (3) a question that already looked the way it was asked to look is **not** counted as changed and its `updated_at` is not bumped, and an id that no longer exists is **counted and reported** (`missing`), never a reason to fail the batch or hide the outcome; (4) class labels are the one list-valued field and support **add / remove / replace** with the same case- and space-insensitive matching and the same 10-label ceiling as `save_question`; (5) a bulk change acts on **explicit ids** — "select all matching" reads the ids, it does not send a filter to the server — and the screen refuses a result over **500** questions, saying the filter is too wide, rather than quietly acting on the first 500; (6) the answer is always `{matched, updated, unchanged, missing}`, so the screen can never say "success" for a partly-applied change; (7) **a bulk change never deletes and never touches the question text, answers, explanation, reading text or files** — archive/restore is the destructive end of it.
- Reason: this is the only shape that keeps the promises the feature makes (all-or-nothing, an honest count, one thing in the audit trail) while staying inside the existing architecture: an Edge Function that validates and calls, a database function that owns the rules, and no new table, no new endpoint and no second way to write a question. Refusing a >500 selection is deliberately less clever than trimming it: a teacher who ticked "all 842" and got 500 changed questions has been lied to, and would not necessarily find out.
- Alternatives: (a) a loop of `save_question` calls from the Edge layer (rejected — partial application, forty audit rows, and it would rewrite fields nobody asked to change); (b) a `sentinel` value such as `"__KEEP__"` for untouched fields (rejected — the database would have to know the word, and a topic could in principle be called that); (c) accept a filter instead of ids and let the server resolve the selection (rejected for now — it makes "what exactly did I change?" unanswerable to the teacher, and the preview step needs a count they can see before they commit); (d) trim a large selection to 500 with a warning (rejected — silent partial work); (e) include a permanent bulk delete (rejected — deleting forty questions in one unconfirmed act is not a feature worth having, and results keep pointing at questions, DEC-005); (f) bulk-edit the question text and answers (rejected — a per-question decision, and sharing a reading text across questions is the duplicate-groups problem instead); (g) a second "bulk" Edge function (rejected — the action belongs in the `question-bank` function that already owns every question write, and a second endpoint is the duplication `00_AI_RULES` forbids).

## DEC-036 — Changing an exam's question set is its own act (`bulk_exam_questions`), the same selection-and-preview pattern the bank uses, and an exam's list is always 1..n
- Date: 2026-09-28 (bulk question management session; SQL written and **applied + live-verified the same day**, twice — the second apply is the renumber fix; see `docs/sql-exam-questions.md`).
- Context: F-17 gave the question bank a bulk path (`bulk_update_questions`, DEC-035). The other half of the ask is the exam's own question set: a teacher looking at an exam — or at a page of ticked questions in the bank — must be able to **put many questions on one exam, or take many off it**, in one act, with the same see-it-before-it-happens step. The obvious shortcut is to reuse `save_exam`, which already writes `exam_questions`; the other is a loop of `save_exam` calls, one per question.
- Decision: (1) **`save_exam` stays the editor's whole-exam write and is not reused for this** — from the bank it would mean rebuilding an entire exam payload (rules panel included) out of data the screen does not hold, and one call per question would rewrite the list from an increasingly stale snapshot; (2) the act is **one database function, one transaction, one audit entry** — `public.bulk_exam_questions(p_exam_id uuid, p_mode text, p_ids uuid[], p_actor uuid)` follows DEC-004 as `save_question` does, and the trail records one `exam.questions` act with the real count, **never an `exam.update`** (nothing about the exam changed, its question list did) and never one row per question; (3) **add and remove are one function with a `p_mode`, not two** — the same act on the same table behind the same guards, and two functions would be two places for those guards to drift; (4) the selection is **explicit ids, never a filter**, capped at the same **500** the bank's bulk path uses, because "what exactly did I change?" has to be answerable and the preview needs a count before anything is committed; (5) the answer is `{matched, updated, unchanged, missing}`, so a repeated act reports `updated 0` and an id that no longer exists is counted and reported rather than failing the batch; (6) the refusals are the exam's own rules — a non-manual (`auto`) selection has no fixed list to change, a **running** exam's questions are what students are answering right now, an exam that **already has attempts** keeps its set and is told to **duplicate** (BR-10 / DEC-012: attempts are never rewritten), an **archived** question cannot be added (the same rule `save_question` enforces for a new exam), and an exam may not grow past the **200** questions `parseExamQuestions` already enforces, so the two paths cannot drift; (7) **an exam's list is always 1..n with no gaps** — adding appends in the order given carrying each question's own `default_weight`, and **removing closes the gap while keeping the survivors' order and points**; (8) the frontend **reuses the F-17 pattern instead of writing a second one** — one shared `components/examQuestionsDialog.js` (choose → preview → apply) opened from both the exam editor and the question bank, with the exam choice skipped when it is already editing that exam, and questions already on it marked and untickable; (9) **the order is chosen in the editor's own list, and nowhere else** — that list is what `save_exam` is given and `save_exam` numbers a manual exam from that payload, so every row carries a **reorder grip** that drags (the row moves under the pointer, the draft catches up on release, `Escape` puts the order back) **and** is the keyboard control (Tab reaches it, ↑ ↓ move one place, Home/End jump to the ends, focus follows the row, each move announced through a polite live region); the `↑`/`↓` buttons and the grip go through the same `moveQuestion`, so the ways of moving a question cannot drift; and like every other edit on that screen a reorder reaches the server only on Save, which is what keeps "one act, one audit entry" true for the bulk function and leaves ordering to the thing that already owns it.
- Reason: this keeps every promise the feature makes — all-or-nothing, an honest count and one thing in the audit trail — inside the existing architecture (an Edge Function that validates and calls, a database function that owns the rules, no new table and no second endpoint). The dense-numbering rule is the one that has to be written down because it is a choice: a gap is *representable* in the schema, but the editor prints `position + 1` as a question's number, `save_exam` already rewrites the list as one contiguous run, and the fallback ordering (`created_at`) is not the order the exam asks its questions in — so position is the only truth and it is kept dense.
- Alternatives: (a) a loop of `save_exam` calls from the browser (rejected — partial application, a stale snapshot per write, one `exam.update` per question, and it would rewrite fields nobody asked to change); (b) reuse `save_exam` once from the bank with a rebuilt payload (rejected — the bank does not hold the exam's rules, so the screen would be guessing at fields it never showed); (c) two functions, `add_exam_questions` and `remove_exam_questions` (rejected — the guards are identical and would drift); (d) accept a filter ("all questions matching this") instead of ids (rejected, as in DEC-035 — the preview needs a visible count, and the audit entry should name exactly what was selected); (e) let remove leave gaps and renumber only on the next Save (rejected — the exam is briefly wrong on screen and in any export, and the reader has to know which writer renumbers); (f) renumber on add as well by rewriting the whole list (unnecessary — appending already produces 1..n); (g) a second dialog component for exams (rejected — `00_AI_RULES` forbids two implementations of one behaviour; the shared dialog is the point of F-18 being "the same pattern"); (h) allow adding an archived question with a warning (rejected — archiving is how a question is retired and `save_question`'s rule is categorical).
- Consequences: `supabase/migrations/20260928000002_bulk_exam_questions.sql` (one function, additive — no table, no column, `save_exam` untouched), the `bulk_questions` action in the `exams` handler, `parseBulkQuestions` in `parse.ts`, `exams.bulkQuestions(...)` in the frontend API, the pick-questions affordance in `examEditor.js`, the add-to/remove-from-an-exam entry in `questionBank.js`, the shared `components/examQuestionsDialog.js`, CSS in `questions.css`, a `bulk_questions` handler in the mock server with the same rules (including the renumber), `docs/sql-exam-questions.md`, and the F-18 row in `03_FEATURES.md`.
