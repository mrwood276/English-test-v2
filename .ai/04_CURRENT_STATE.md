## Bulk question management (2026-09-28, twenty-sixth session — Buffy, no live access)

The brief: a teacher must be able to change many questions at once instead of one at a time — **select → filter → bulk edit → preview → apply → feedback**, end to end, without breaking the single-question paths or inventing a second API.

What was built, and where:

- **SQL, one act:** `supabase/migrations/20260928000001_bulk_question_update.sql` adds `public.bulk_update_questions(p_ids uuid[], p_changes jsonb, p_actor uuid)`. It is **additive** — one function, no table, no column, no change to `save_question` or `set_question_archived` — and it returns `{matched, updated, unchanged, missing}`. Only rows that really differ are written, so `updated` is the truth and no `updated_at` is bumped for nothing; ids that no longer exist are counted, not fatal; a selection that matches nothing is refused; **one audit entry per call** (`question.bulk_update`, with the real count and what was asked for). Only `service_role` may execute it (`revoke … from public, anon, authenticated`). Contract: `docs/sql-bulk-update.md`.
- **Edge:** `question-bank` gained the `bulk_update` action; `parseBulkUpdate` (in `parse.ts`) **whitelists** the five possible keys (`topic`, `difficulty`, `weight`, `archived`, `class_labels`), so a caller cannot smuggle `body`, `options` or `content_hash` through a bulk change, dedupes the ids, caps the selection at 500 and requires at least one real change. Authorisation is the existing `requireStaff` door — no new path, no new privilege.
- **Screen:** `questionBank.js` got per-row checkboxes, a header checkbox (with the half-ticked state), a selection counter that also says how much of the selection is **not on this page**, a bulk bar with `Edit…`/`Archive`|`Restore`/`Clear`, and the offer *"All 25 questions on this page are selected. → Select all 28 matching questions"*, which fetches the whole filter result in as few requests as the list API allows. A filter change **keeps** the ticks (the ids are explicit and the counter says where they are); the archived switch **clears** them, because it flips what the bar's button would mean. Over 500 matching questions the screen says the filter is too wide and changes nothing rather than quietly acting on the first 500.
- **Dialog:** `components/bulkEditDialog.js` — every field starts on "keep as it is" (and an untouched field is **not sent at all**, so "keep" is never a value the database has to interpret), then a second step that names the count, each change and each thing left alone (`42 questions will be affected.`) before `Apply changes`. Class labels support add / remove / replace; topic can be set to a new or existing name or cleared; points and difficulty follow the existing rules. A failure is shown inside the dialog, which stays open with its buttons usable again.
- **Tests:** backend `question_bank.test.ts` +6 (parser whitelist/refusals, one call with the right actor, a validation 400 vs a hidden 500, a tokenless 401 with zero database calls) → **153**; `question_bank_e2e.py` +62 (selection, paging, filter interplay, select-all-filtered, preview wording, the applied payload, partial and missing results, a refused change and a retry, bulk archive/restore behind a confirm dialog, the 500 guard, and the bar on a phone) → **129**; `mock_server.py` gained a `bulk_update` handler with the same rules. Twelve other suites unchanged and green.

## How SQL business rules were tested (technique)

Because the live database is the only database, SQL tests are `DO` blocks executed with the Supabase `execute_sql` tool that create data, assert results (including that invalid input is refused with the expected message and `validation` hint), and end with `RAISE EXCEPTION 'X_TESTS_PASSED'` so the whole transaction rolls back. A returned error message that starts with the pass marker means success and nothing persists. After such a run the row counts in "Live system facts" must be unchanged.
