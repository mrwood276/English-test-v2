## ISSUE-016 — Session-expired notice could be overwritten by a second announcement (real product bug behind the CI flake)
- Severity: MEDIUM (was misdiagnosed LOW twice). Status: **FIXED-AT-ROOT (2026-09-22, second fix)**.
- History: first "fixed" by making the editor test wait for the notice text (still flaked: CI run #4 on commit `87acd3b` failed the Question-editor step with a 30 s `wait_for_function` timeout). Reproduced locally 1-in-2 when running the full suite chain.
- Root cause (product, not test): every `SessionExpiredError` dispatched `staff:session-expired`. After a 401 the session is cleared, so any later background request (the editor's debounced duplicate-check timer fires ~600 ms after typing, even detached from the removed screen) throws `SessionExpiredError("Please sign in.")` and re-dispatches, and `app.js` re-renders the login screen **replacing the first notice** ("Your session has expired...") with "Please sign in." The test waits for the first text and times out. Slow CI machines lose the race; fast local ones read the notice before the overwrite.
- Fix (core/api.js): announcements are gated by a module flag `sessionExpiredAnnounced` — only the first error per signed-out period announces; the flag resets on `staff:signed-in`, dispatched in `app.js#showApp` (single choke-point after every sign-in/boot path). Behavior is unchanged for users: they still land on sign-in with the first explanation; later redundant re-renders are gone.
- Verification: 3 consecutive full browser chains (all 5 suites) pass 15/15 (crashed on cycle 2 before the fix); unit 21/21; `deno check` clean.

## ISSUE-022 — The Frontend job failed twice at the same exams check (reload raced the router's URL hand-off)
- Severity: MEDIUM (a red CI run that was not a product regression — but it hid real ones for a day). Status: **FIXED (2026-09-25, git `7a5b09e`)**.
- Description: Frontend tests failed on `f4eb5e7` and `2f5de2c`, both at `frontend/tests/exams_e2e.py` line 141 with `FAIL existing exam title loaded`, followed by a 30 s `TimeoutError` waiting for `.chosen-item`. The next commits (docs-only) were green, which made it look random.
- **Cause**: the suite did `page.goto(BASE + "#/exams/edit/" + EXAM1); page.reload()` — a reload immediately after a hash-only navigation. `router.js` answers every hash change from a guarded screen by putting the **current** hash back (`history.replaceState(null, "", currentHash)`) while it hands the navigation to the leave guard, so a reload landing in that window reloads the *previous* screen. Here that was the just-saved draft (`0003`, title `Simple Past, Quiz 1`, saved in "draw by filter" mode) — hence the wrong title and no `.chosen-item` ever appearing. It was timing-dependent, which is why it passed locally and in most CI runs.
- **Fixes**: (1) `guard.js`/`router.js` now ask, and hold the URL, only while something is really unsaved (`setLeaveGuard(fn, hasUnsavedWork)`, `hasUnsavedChanges()`), so a clean screen navigates straight through; (2) the suite loads the target screen and waits for it **before** reloading, and checks that an untouched editor reloads with no leave warning. With the old semantics restored, the suite dies at that reload (`Page.reload` timeout after 21 checks).
- **Note for test authors**: never `goto(hash)` and `reload()` in the same breath. Wait for something only the target screen has, then reload. `page.reload()` can also hang (30 s, then `TimeoutError`) when a `page.on("dialog")` listener is registered and a `beforeunload` warning fires — verified with a standalone probe on 2026-09-25.
- Unrelated, still open: `question_editor_e2e.py` can fail once when a click races a toast animation (`<html> intercepts pointer events`) and passes on re-run (noted 2026-09-24).

## ISSUE-025 — `question_editor_e2e.py` fails in CI on its last click, once in a while, with everything else green
- Severity: LOW (test-only) but **it hides real regressions**: a red Frontend run has to be diagnosed every time, and this project has already burned runs on ISSUE-022 for the same reason. Status: OPEN.
- **Seen on `b799af1` (2026-09-25)** — a **docs-only** commit whose identical product code was green on `5252359` minutes earlier, which is what proves it is a flake and not a regression. CI run `36137217451`, job `browser`, step "Question editor": every check PASSed (including the last, `answer buttons are large enough to tap`), then
  `playwright._impl._errors.TimeoutError: Page.click: Timeout 30000ms exceeded … waiting for locator("button:has-text('Save question')") … element is not stable … element was detached from the DOM, retrying`.
- Already noted on 2026-09-24 as "can fail once when a click races a toast animation (`<html> intercepts pointer events`) and passes on re-run". Both symptoms are the same race: the editor screen rebuilds its tree (a save response and its toast arrive while the click is in flight), so Playwright keeps retrying against a detached button until the 30 s timeout. The earlier note guessed at the toast; the CI log above names the real mechanism (detached/unstable node).
- **Not reproduced locally**: `question_editor_e2e.py` is 75/75 here, repeatedly, and green again on the re-run of that same CI job. A race this rare cannot be "fixed" blind — the wrong repair is how the earlier misdiagnoses happened (ISSUE-016, ISSUE-022).
- **Suggested fix, for a session that can watch it fail**: the router already stamps `container.dataset.render` on every render, so a robust click would wait for the screen to settle (or for the render stamp to stop changing) instead of clicking a node that is about to be replaced — e.g. click only after the first render following the previous save has settled, or retry the whole `click` on `element was detached` up to a few times. Do **not** just raise the timeout; that turns a visible race into a slow one.
- Affected: `frontend/tests/question_editor_e2e.py`. Related: ISSUE-022.
